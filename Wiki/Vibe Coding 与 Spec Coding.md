# Vibe Coding 与 Spec Coding

## 两种模式解决的是不同问题

**Vibe Coding** 以当前对话为中心：描述目标，让 AI 快速实现，再根据结果继续修正。它优化的是即时反馈和探索速度。

**Spec Coding** 以仓库中的项目事实为中心：先把重要需求、约束、设计和验收条件显式化，再让 AI 依据这些材料实施、检查并沉淀经验。它优化的是跨会话一致性、可维护性和可追溯性。

两者不是非此即彼。合理做法是根据任务风险和维护周期选择流程重量。

## 快速判断

| 判断维度 | 更适合 Vibe Coding | 更适合 Spec Coding |
| --- | --- | --- |
| 生命周期 | 一次性、短期实验 | 长期维护、持续迭代 |
| 失败成本 | 低，出错后容易重来 | 高，涉及用户、数据或多个模块 |
| 任务范围 | 局部、边界清楚 | 跨模块、多决策、多阶段 |
| 协作方式 | 单人、无需交接 | 多人协作或经常交接 |
| 上下文 | 一次会话足够 | 需要跨会话、跨工具恢复 |
| 知识价值 | 结果可丢弃 | 决策和经验值得复用 |

## Vibe Coding 的结构性风险

单轮产出可能正确，但多轮局部修改容易累积以下问题：

- 重复逻辑和特殊分支持续增加；
- 新实现绕开已有架构边界；
- 历史决策与权衡只存在于聊天记录中；
- 新会话只能从代码结果倒推设计意图；
- AI 工具切换后，平台专属规则和工作记忆难以迁移。

问题的根源通常不是模型不够聪明，而是模型没有稳定、可验证的项目上下文。

## 最小可行的 Spec Coding

Spec Coding 不一定需要完整框架。一个长期项目至少可以保留四类材料：

1. **规范**：长期有效的架构边界、接口约定、测试规则和禁止事项。
2. **任务**：本次变更的目标、范围、验收条件、设计与实施计划。
3. **决策**：为什么采用当前方案、放弃了哪些替代方案。
4. **验证与收尾**：测试结果、规范检查、未决问题，以及需要回流到长期规范的经验。

一个轻量流程可以是：

```text
澄清目标 → 写验收条件 → 形成实施计划 → 实现与验证 → 更新稳定规范 → 记录未决事项
```

只有当跨会话恢复、多人协作或经验回流成为真实痛点时，才需要进一步引入 [[Trellis：项目级 Spec Coding 闭环]] 这类项目级 Harness。

## 与 SDD、TDD 和 Skill 的关系

- **Spec-Driven Development（SDD）**强调先明确 WHAT/WHY，再设计 HOW 和拆分 DO，是 Spec Coding 的核心方法之一。
- **测试驱动开发（TDD）**约束实现阶段如何获得可验证反馈，并不能代替需求与架构规范。
- **Rules / AGENTS.md / CLAUDE.md**适合保存长期静态约束，但通常不负责当前任务状态。
- **Skill**适合固化某类工作方法，例如澄清、调试、测试和审查，但不天然保存项目记忆。
- **Harness**把上下文、状态、工具和工作流连接起来，使这些材料在每次任务中真正被读取和更新。

## 核心原则

> Spec Coding 的目标不是增加文档，而是让高价值的项目事实脱离临时对话，成为人和 AI 都能持续使用的工程资产。
