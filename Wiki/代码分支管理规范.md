# 代码分支管理规范

> 版本: 3.0.0 | 更新日期: 2026-03-20
> 分支模型: **GitLab Flow + Release Branch**

---

## 1. 分支模型概述

采用 GitLab Flow 作为基础，叠加 Release Branch 能力以支持多版本并行维护。

不为开发环境和测试环境创建额外分支，而是通过 CI 触发规则将 `main` 和 `staging` 分支自动部署到对应环境，保持分支策略简洁。

### 1.1 分支全景图

```
feature/*  ──┐
bugfix/*   ──┤
             ├──> main (开发主干) ──────────────> [自动] 部署到开发环境
hotfix/*   ──┘      │
                    ├──> staging (预发布) ──────> [自动] 部署到内部测试环境
                    │                             [手动] push 到客户 staging
                    │       └──> production ────> [手动] push 到客户 production
                    │
                    ├──> release/v1.5 (长期维护版本)
                    ├──> release/v1.6
                    └──> release/v1.7
```

### 1.2 环境与分支映射

| 环境 | 用途 | 使用者 | 部署来源 | 触发方式 |
|------|------|--------|---------|---------|
| **开发环境 (dev)** | 开发者自测，始终运行最新代码 | 开发团队 | `main` 分支 | MR 合并到 main 后**自动部署** |
| **内部测试环境 (test)** | QA 验收测试 | QA 团队 | `staging` 分支 | 合并到 staging 后**自动部署** |
| **客户 Staging** | 客户 UAT / 最终验证 | 客户 | `staging` 分支 | **手动**点击 push job |
| **客户 Production** | 正式对客户提供服务 | 客户 | `production` 分支 | **手动**点击 push job |

> 开发环境和内部测试环境是团队内部使用的环境，通过 CI 自动部署，不需要额外的分支。
> 客户 Staging 和客户 Production 是面向客户的环境，通过手动 push 控制发布节奏。

### 1.3 运行模式

| 模式 | 适用场景 | 涉及分支 |
|------|---------|---------|
| **常规模式** | 所有客户使用最新版本 | `main → staging → production` |
| **版本锁定模式** | 某些客户锁定在特定版本 | `release/vX.Y` 独立维护和部署 |

常规模式是日常默认流程。版本锁定模式在客户明确要求时启用。

## 2. 分支定义

### 2.1 永久分支

| 分支           | 用途               | 自动部署目标 | 保护规则                             |
| ------------ | ---------------- | ------ | -------------------------------- |
| `main`       | 开发主干，所有功能最终汇入此分支 | 开发环境   | 禁止直接推送，必须通过 MR，至少 1 人 Approve    |
| `staging`    | 预发布验证            | 内部测试环境 | 禁止直接推送，只接受从 main 合并              |
| `production` | 生产环境，对应最新版本的生产部署 | —      | 禁止直接推送，Maintainers only 通过 MR 合并 |

### 2.2 版本分支（按需创建）

| 分支 | 用途 | 保护规则 |
|------|------|---------|
| `release/vX.Y` | 锁定版本的长期维护分支 | 禁止直接推送，只接受 cherry-pick 的 hotfix |

### 2.3 临时分支

| 分支 | 用途 | 来源 | 合并目标 | 命名示例 |
|------|------|------|---------|---------|
| `feature/*` | 功能开发 | `main` | `main`（通过 MR） | `feature/user-auth` |
| `bugfix/*` | 非紧急 bug 修复 | `main` | `main`（通过 MR） | `bugfix/fix-pagination` |
| `hotfix/*` | 生产紧急修复 | `production` | `production`（通过 MR） | `hotfix/fix-crash-on-login` |

所有临时分支合并后必须删除。

## 3. 分支权限矩阵

| 分支 | 直接推送 | MR 合并 | 合并前要求 |
|------|---------|---------|-----------|
| `main` | 禁止 | Developers+ | CI 通过 + 至少 1 人 Approve |
| `staging` | 禁止 | Developers+ | 只接受来自 main 的合并 |
| `production` | 禁止 | Maintainers only | CI 通过 + 至少 1 人 Approve |
| `release/vX.Y` | 禁止 | Maintainers only | CI 通过 + 至少 1 人 Approve |
| `feature/*` | 创建者 | — | — |
| `bugfix/*` | 创建者 | — | — |
| `hotfix/*` | 创建者 | — | — |

## 4. 工作流程

### 4.1 功能开发（日常）

```
┌─────────┐    MR + Review     ┌──────┐    自动部署
│ feature/ ├──────────────────>│ main ├──────────────> 开发环境
└─────────┘                    └──┬───┘
                                  │ merge
                                  v
                             ┌─────────┐    自动部署
                             │ staging ├──────────────> 内部测试环境
                             └────┬────┘
                                  │ MR
                                  v
                           ┌────────────┐   手动 push
                           │ production ├─────────────> 客户生产环境
                           └────────────┘
```

```bash
# 1. 从 main 创建功能分支
git fetch origin
git checkout -b feature/user-auth origin/main

# 2. 开发、提交
git add .
git commit -m "新增: 用户认证模块"

# 3. 推送并创建 MR
git push origin feature/user-auth
# 在 GitLab 创建 MR: feature/user-auth → main
# 等待 CI 通过 + 至少 1 人 Approve 后合并

# 4. 合并后 main 自动部署到开发环境，开发者可立即自测

# 5. 清理分支
git checkout main
git pull origin main
git branch -d feature/user-auth
git push origin --delete feature/user-auth
```

### 4.2 发布到内部测试环境

将 main 合并到 staging 后，CI 自动部署到内部测试环境供 QA 验收。

```bash
# 将 main 合并到 staging
git fetch origin
git checkout staging
git pull origin staging
git merge origin/main --no-edit
git push origin staging
git checkout main

# staging 分支自动部署到内部测试环境，QA 开始验收
```

### 4.3 发布到客户 Staging

QA 验收通过后，在 GitLab 流水线页面手动点击对应客户的 push job，将镜像推送到客户 staging 环境。

### 4.4 发布到客户 Production

**production 分支禁止直接推送，必须通过 MR。**

```
1. 在 GitLab 创建 MR: main → production
   - Title: "deploy: release vX.Y.Z to production"
   - 不要勾选 "Delete source branch"

2. 等待 CI 通过 + Maintainer Approve

3. 合并 MR

4. 在 GitLab Web UI 手动点击需要的 push job
```

### 4.5 紧急热修复 (Hotfix)

```bash
# 1. 从 production 创建 hotfix 分支
git fetch origin
git checkout -b hotfix/fix-crash-on-login origin/production

# 2. 修复并提交
git add .
git commit -m "修复: 登录时崩溃问题"
git push origin hotfix/fix-crash-on-login

# 3. 创建 MR: hotfix/fix-crash-on-login → production
#    Maintainer Approve 后合并

# 4. 合并后必须同步回 main
git checkout main
git pull origin main
git merge origin/production --no-edit
git push origin main

# 5. 如果有 release 分支也受影响，cherry-pick 到对应分支（见第 5 章）

# 6. 清理
git branch -d hotfix/fix-crash-on-login
git push origin --delete hotfix/fix-crash-on-login
```

### 4.6 回滚

**自动回滚**：每个 deploy job 内置失败自动回滚机制。

**手动回滚**：
- 在对应云平台控制台操作（ECS / SAE / TKE）
- 或在 GitLab 流水线页面重新触发上一个成功 commit 的 deploy job

## 5. Release Branch — 多版本并行维护

### 5.1 何时使用

当客户明确要求锁定在某个版本、不随主线升级时，为该版本创建 release 分支。

**不要提前创建。** 在客户提出版本锁定需求时才创建。

### 5.2 创建 Release 分支

```bash
# 从 main 的稳定点切出（通常是刚发布到 production 后的 commit）
git fetch origin
git checkout -b release/v1.5 origin/main

# 打 tag 标记版本起点
git tag -a v1.5.0 -m "Release v1.5.0"
git push origin release/v1.5 --tags
```

创建后在 GitLab 设置分支保护：禁止直接推送，Maintainers only 通过 MR 合并。

### 5.3 Release 分支的 Bug 修复

**原则：所有修复先进 main，再 cherry-pick 到 release 分支。永远不要直接在 release 分支上开发修复。**

```
修复流程:
  hotfix/* → main（先修主干）
           → cherry-pick 到 release/v1.5（按需回移）
           → cherry-pick 到 release/v1.6（按需回移）
```

```bash
# 1. 修复已经合并到 main（通过常规 hotfix 流程）
# 假设修复的 commit hash 是 abc1234

# 2. Cherry-pick 到需要的 release 分支
git fetch origin
git checkout release/v1.5
git pull origin release/v1.5
git cherry-pick abc1234

# 如果有冲突，手动解决后：
# git add .
# git cherry-pick --continue

git push origin release/v1.5

# 3. 更新 patch 版本号
git tag -a v1.5.1 -m "Patch v1.5.1: fix crash on login"
git push origin --tags
```

也可以在 GitLab Web UI 操作：在 main 分支的 commit 页面点击 "Cherry-pick" 按钮，选择目标 release 分支。

### 5.4 客户版本映射示例

| 客户 | 使用版本 | 部署来源分支 |
|------|---------|------------|
| dazee-ai | 最新版 | `production` |
| dazee-cc | 最新版 | `production` |
| 17gongchuang | v1.5（锁定） | `release/v1.5` |
| opschatai | v1.6（锁定） | `release/v1.6` |

### 5.5 版本支持策略

| 规则 | 说明 |
|------|------|
| 最大并行版本数 | 建议不超过 **3 个** release 分支 |
| 版本支持周期 | 创建后最长维护 **6 个月**，到期后与客户协商升级 |
| 过期处理 | 归档 tag → 删除 release 分支 → 更新客户部署映射 |

### 5.6 Cherry-pick 检查清单

每次 hotfix 合并到 main 后，负责人必须检查：

- [ ] 该修复是否影响现有的 release 分支？
- [ ] 列出需要 cherry-pick 的 release 分支：`release/v___`
- [ ] 每个 release 分支 cherry-pick 完成后，是否更新了 patch 版本 tag？
- [ ] 是否触发了对应 release 分支的部署流水线？

## 6. 版本号规范

采用 [语义化版本](https://semver.org/lang/zh-CN/) (Semantic Versioning)：

```
vMAJOR.MINOR.PATCH
```

| 版本段 | 含义 | 递增时机 |
|--------|------|---------|
| MAJOR | 不兼容的 API 变更 | 破坏性变更（数据库 schema 不兼容、API 删除等） |
| MINOR | 向下兼容的功能新增 | 新功能、新 API 端点 |
| PATCH | 向下兼容的 bug 修复 | bug 修复、安全补丁 |

**Tag 规范**：

```bash
# 正式版本（创建 release 分支时）
git tag -a v1.5.0 -m "Release v1.5.0"

# 补丁版本（cherry-pick 修复后）
git tag -a v1.5.1 -m "Patch v1.5.1: fix description"

# 预发布版本（可选）
git tag -a v1.6.0-rc.1 -m "Release candidate v1.6.0-rc.1"
```

**打 tag 的时机**：
- 创建 release 分支时打 `vX.Y.0`
- 每次 cherry-pick 修复到 release 分支后打 `vX.Y.Z`（递增 PATCH）
- production 分支的重要发布点也建议打 tag


## 8. 多人协作规范

### 8.1 分支生命周期

- feature / bugfix 分支存活不超过 **3-5 天**
- 如果功能需要更长时间，拆成多个小 MR 分批合并到 main
- 每天从 main rebase 一次，保持分支和主干同步：

```bash
git fetch origin
git rebase origin/main
```

### 8.2 Merge Request 规范

**提交 MR 前**：

- 从 main rebase 到最新，确保没有冲突
- 本地跑通编译和单元测试（`make test-unit`）
- MR 描述写清楚：改了什么、为什么改、怎么测试

**Review 规则**：

- 至少 **1 人 Approve** 才能合并
- Reviewer 在 **24 小时内**完成 Review，避免阻塞
- 单个 MR 不超过 **400 行**改动（不含自动生成的文件），超过则拆分

**合并方式**：

- 推荐使用 **Squash and merge**，保持 main 的 commit 历史干净
- 合并后自动删除 feature 分支

### 8.3 高冲突风险文件

以下文件容易产生多人冲突，需要特别注意：

| 文件 | 风险原因 | 应对策略 |
|------|---------|---------|
| `cmd/server/wire/wire.go` | Wire 依赖注入，多人新增模块时冲突 | 改完后立即提 MR，不要在 feature 分支上积压 |
| `internal/router/web.go` / `admin.go` | 路由注册，多人新增接口时冲突 | 同上，优先合并 |
| `config/secrets.enc.yml` | SOPS 加密的二进制文件，冲突无法手动解决 | 由专人负责修改，禁止多人同时编辑 |
| `.gitlab-ci.yml` 及 `.gitlab/ci/*.yml` | CI/CD 配置，改错影响所有环境 | 由指定负责人修改，需要额外 Review |

### 8.4 禁止事项

- **禁止**绕过 main 直接往 staging 或 production 推送代码
- **禁止**在 staging 上修 bug 而不经过 main
- **禁止**手动在服务器上改代码
- **禁止**force push 到任何受保护分支

所有代码变更的**唯一入口是 main 分支**。staging 和 production 只接受从 main 合并过来的代码。

### 8.5 合并冲突处理

| 场景 | 处理方式 |
|------|---------|
| feature 分支和 main 冲突 | 在 feature 分支上 rebase main，由 feature 分支的开发者解决 |
| main 合并到 staging 冲突 | 不应该发生（staging 只接受 main 的合并）。如果发生，说明有人绕过了流程 |
| main 合并到 production 冲突 | 创建临时分支 `merge-main-to-production` 解决冲突后通过 MR 合并 |
| cherry-pick 到 release 分支冲突 | 手动解决，如果冲突过大则推动客户升级 |

### 8.6 关键操作责任人

| 操作 | 责任人 | 备注 |
|------|--------|------|
| MR Review | 团队成员轮流 | 24 小时内完成 |
| 合并到 staging | 任意 Developer | 确认所有待发布 MR 已合并到 main |
| 合并到 production | Maintainer | 必须通过 MR + Approve |
| 修改 CI/CD 配置 | 指定负责人 | 高风险文件，需要额外审慎 |
| 修改 SOPS 密钥 | 指定负责人 | 二进制文件，不可多人并行 |
| cherry-pick 到 release 分支 | Maintainer | 需要同时更新 patch tag |

### 8.7 每日协作沟通

- **开发前**：确认谁在改哪个模块，避免两个人同时改同一块代码
- **提 MR 后**：主动通知 Reviewer，不要等对方自己发现
- **发布前**：确认所有待合并的 MR 都已合并到 main，不要在 staging 上"等"某个还没合并的功能

## 9. 常见问题

### Q: 为什么不为开发环境和测试环境创建单独的分支？

增加 develop / testing 分支会导致永久分支从 3 个变成 5 个，合并链从 3 次变成 5 次，且 develop / testing 分支容易和 main 分叉。通过 CI 触发规则让 main 自动部署到开发环境、staging 自动部署到测试环境，效果相同但复杂度更低。

### Q: 开发环境和内部测试环境的区别？

开发环境运行 main 分支最新代码，每次 MR 合并后自动更新，供开发者自测。内部测试环境运行 staging 分支代码，是 QA 正式验收的环境，代码比开发环境更稳定。

### Q: 什么时候创建 release 分支？

客户明确提出版本锁定需求时。不要提前创建。

### Q: release 分支的 bug 修复流程？

先修 main（通过常规 hotfix 流程），再 cherry-pick 到受影响的 release 分支。**永远不要直接在 release 分支上开发修复。**

### Q: 如何判断一个 hotfix 需要 cherry-pick 到哪些 release 分支？

检查该 bug 在哪些版本中存在。如果 bug 是 v1.4 引入的，那么 `release/v1.4`、`release/v1.5`、`release/v1.6` 都需要 cherry-pick。

### Q: release 分支越来越多怎么办？

与客户约定版本支持周期（建议 6 个月），到期后协商升级到最新版本，归档并删除过期的 release 分支。建议同时维护不超过 3 个 release 分支。

### Q: cherry-pick 有冲突怎么办？

手动解决冲突后 `git cherry-pick --continue`。如果冲突过于复杂，说明 release 分支和 main 的差异过大，应优先推动客户升级。

### Q: staging 环境验证的是哪个版本？

staging 始终验证 main 分支的最新代码（即下一个要发布的版本）。release 分支的修复通过 release 分支自己的流水线验证，不经过 staging。

## 10. 完整发布流程

```
  feature/* ─── MR ───> main ─────────────────────────────────────────────>
                         │                                                │
                    [自动部署]                                            │
                         │                                                │
                    开发环境 (dev)                                         │
                    开发者自测                                             │
                         │                                                │
                    确认后 merge                                          │
                         v                                                │
                      staging ────────────────────────────────>           │
                         │                        │                       │
                    [自动部署]               [手动 push]                   │
                         │                        │                       │
                  内部测试环境 (test)         客户 Staging                  │
                    QA 验收                  客户 UAT                      │
                         │                        │                       │
                    验收通过                  客户确认                      │
                         │                        │                       │
                         └────────────────────────┘                       │
                                      │                                   │
                                 MR 合并到                                │
                                      v                                   │
                                 production ──── [手动 push] ──> 客户生产环境
```

## 11. 流程速查表

| 我要... | 操作 |
|---------|------|
| 开发新功能 | `feature/*` → MR → `main` → 自动部署到开发环境 |
| 修复非紧急 bug | `bugfix/*` → MR → `main` → 自动部署到开发环境 |
| 提交 QA 测试 | `main` → merge → `staging` → 自动部署到内部测试环境 |
| 发布到客户 Staging | 在 staging 流水线手动点击 push job |
| 发布到客户 Production | `main` → MR → `production` → 手动点击 push job |
| 紧急修复生产 | `hotfix/*` → MR → `production` → 同步回 `main` |
| 锁定客户版本 | 从 `main` 切 `release/vX.Y` → 打 tag |
| 修复 release 版本 | 先修 `main` → cherry-pick 到 `release/vX.Y` → 打 patch tag |
